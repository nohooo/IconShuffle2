这句话有两个问题，而且都不是我猜的，是你指定的那个参考项目自己在 README 里写的：

你的假设参考项目的实际说法

即：这条路他们也没验证成功过。
「读取」应该没问题，只是写入要权限 该项目 P5 阶段的实测结论：

即：以 shell 身份运行的 Shizuku，连读都读不到。
桌面是 Launcher3 你的机器是 com.miui.home（HyperOS 桌面），不是 AOSP Launcher3，
favorites 表的列集合与 AOSP 有差异。
— 该项目真正跑通并落地的主路径是路径 ⑤：Launcher3 官方「布局提供者」通道
（launcher3.layout.provider + ContentProvider + 布局 XML 导入），免 root、瞬时。

该项目自己给这条产品路线打的注脚是：

「未在真机验证 —— 真机 Shizuku 走无线调试；厂商 ROM 是否保留该通道未知，是最大产品风险」
为什么 shell 读不到别人的 /data/data：这是 Android 11+ 的 SELinux 设计，不是「权限没给够」。
launcher.db 的 SELinux 上下文是 app_data_file，而 shell 域只有 MLS 类别 s0， App 的数据文件带 s0:c512,c768。类别不匹配，即使 Unix 权限位是 0777 也照样 EACCES。 Shizuku 以 root 启动时是另一回事（root 绕过 SELinux 检查），所以「能不能跑通」完全取决于 你的 Shizuku 是以 root 还是 wireless-debugging(shell) 启动的。

五、风险与安全设计

  • 自动备份：每次打乱前，先把 launcher.db 复制成 databases/launcher.db.bak-yyyyMMdd-HHmmss，并提供 restore() 回滚。
  • 只改两列：UPDATE favorites SET cellX=?, cellY=? WHERE _id=?，其余列与其它表一个字节不碰。
  • 事务提交：全部换位在一个 SQLite 事务里完成，中途失败不会留半个状态。
  • 写后校验：写完重新打开数据库回读，逐条比对目标坐标，不匹配会明确报告。
  • Dock 默认保护：Dock 图标固定在 container=-101，默认不参与打乱。
  • 不自动重启桌面：默认关闭，避免 HyperOS 上出现黑屏。pkill 能力已实现但需显式开启。

六、打乱语义（已按你的确认修正）

你明确要求四条约束，因此早期实现的「全体池子重排、允许跨页迁移」已被删除。 现在两个模式都满足这四条不变量：

#不变量实现层面如何保证
1总页数不变 算法从不改动 screen 字段，一个字节都不写
2每页占用的格数不变 目标坐标池 = 该页当前占用的坐标集合，打乱只是重排「谁占哪个格」， 因此占格集合按构造恒等
3图标只在页内换位 每个页面被切成独立的组，ShuffleEngine.plan 按 screen 分组后 逐组独立处理
4绝不跨页迁移 每组的候选坐标只来自本组（slots = group.map{...}）， 跨页在数据结构上不可能发生 —— 不是靠事后校验，是取不到别的页的坐标

两个模式的区别只剩「一次处理几页」：

模式行为
打乱所有页面每一页各自独立打乱，一次全部处理完
仅当前页面只处理你正在用的那一页，其余页一个图标都不动
「当前页面」是怎么判断的？
Android 没有公开 API 能问出桌面停在哪一页。本工程用启发式：取 favorites.modified 时间戳最晚的那一页 —— 也就是你刚才操作过的页面（见 LauncherDb.guessCurrentScreen）。
执行前日志会把「每页图标数」和「本次涉及的页面」都打出来，你可以直接核对是否打对了页。 如果推测错了，说明该 ROM 不更新 modified，我再换成让你手动指定页号。
没有为了这个默认值去申请无障碍权限 —— 不划算。

验证方式：ShuffleEngineTest 用 3 页数据（含 1 个跨格 widget） 乘以 30–50 个随机种子，逐条断言上述四条不变量，并额外覆盖 widget 不被移动、 文件夹内部不动、hidden=1 不动、Dock 默认不动、单图标页不产生换位等保护规则。 LauncherDbTest 则验证端到端「读 → 打乱 → 写 → 回读」后 id 集合与占格集合都不变。
